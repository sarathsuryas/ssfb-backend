# SSFB backend

NestJS 12 API (ESM / TypeScript) with Prisma, validated configuration, role-based
email/password authentication using httpOnly cookies, consistent API responses and
OpenAPI docs.

## Getting started

```bash
npm install          # also runs `prisma generate`
cp .env.example .env # then edit the values
npm run prisma:migrate
npm run prisma:seed  # creates the first ADMIN from SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD
npm run start:dev
```

- API: `http://localhost:3000/api`
- Health: `http://localhost:3000/health` and `/health/ready`
- Swagger UI: `http://localhost:3000/docs` (JSON at `/docs-json`)

## Layout

```
prisma/                 Prisma schema, migrations, seed and prisma.config.ts
src/
  config/               env validation + typed configuration (global)
  database/             PrismaService lifecycle + global database module
  common/               exception filter, response interceptor, validation pipe, CsrfGuard, RolesGuard
  auth/                 login/session endpoints, JWT strategy, global guards, decorators
  health/               liveness and readiness probes
  modules/users/        user persistence, provisioning endpoints, protected /users route
  generated/prisma/     generated client (gitignored, regenerated by postinstall)
```

## Roles and provisioning

`ADMIN`, `STAFF` and `CUSTOMER`. There is no public registration — accounts are
provisioned by an authenticated user:

| Actor            | Can create | Endpoint                    |
| ---------------- | ---------- | --------------------------- |
| `ADMIN`          | STAFF      | `POST /api/admin/staff`     |
| `ADMIN`, `STAFF` | CUSTOMER   | `POST /api/staff/customers` |
| `CUSTOMER`       | —          | —                           |

The first ADMIN is created with `npm run prisma:seed`. Permissions are enforced both
by the global `RolesGuard` (`@Roles(...)`) and by `UsersService.createUser`, which also
records `createdById` for audit. A role is never accepted from a request body. Roles
are read from the database on every request, so changes take effect immediately.

## Authentication

Sessions use two httpOnly cookies: `access_token` (15 min, sent to all routes) and
`refresh_token` (7 days, scoped to `/api/auth`). Only a SHA-256 hash of each refresh
token is stored in the database. Refresh tokens rotate on use; replaying a revoked
token revokes every session for that user.

| Endpoint                         | Auth           | Purpose                                         |
| -------------------------------- | -------------- | ----------------------------------------------- |
| `POST /api/auth/login`           | public         | Log in and start a session                      |
| `POST /api/auth/refresh`         | refresh cookie | Rotate the refresh token                        |
| `POST /api/auth/logout`          | session        | Revoke the current refresh token, clear cookies |
| `POST /api/auth/change-password` | session        | Change password, revoke other sessions          |
| `GET /api/auth/me`               | session        | Get the current user (includes `role`)          |
| `GET /api/users`                 | ADMIN, STAFF   | List users                                      |

### CSRF

A readable `csrf_token` cookie is set on login, refresh and change-password. Send its
value as an `X-CSRF-Token` header on every state-changing request. Login is exempt (no
token exists yet), as are requests with an `Authorization: Bearer` header — browsers
cannot attach those cross-site. `JwtAuthGuard` also accepts a Bearer access token,
which is convenient for API testing.

```bash
# log in as the seeded admin (cookies land in cookies.txt)
curl -c cookies.txt -H 'Content-Type: application/json' \
  -d '{"email":"admin@ssfb.local","password":"AdminPass123!"}' \
  http://localhost:3000/api/auth/login

# create a staff account
CSRF=$(awk '$6=="csrf_token"{print $7}' cookies.txt | tail -1)
curl -b cookies.txt -X POST -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' \
  -d '{"email":"staff@example.com","password":"password123"}' \
  http://localhost:3000/api/admin/staff
```

## CORS

Browser access is restricted to the origins in `CORS_ORIGINS` (comma-separated,
default `http://localhost:4200`). Credentials are allowed so the Angular app can send
the httpOnly session cookies; `X-CSRF-Token` is an allowed request header for
state-changing calls. Keep cookie `SameSite=Strict` while the frontend and API are on
the same site; cross-site deployments would need `SameSite=None; Secure` instead.
CORS is not an authorization control — the JWT, role and CSRF guards still apply.

## Conventions

- Business routes are served under `/api`; `/health` and `/docs` are excluded from the prefix.
- Successful responses are wrapped as `{ "data": ... }` by the global response interceptor.
- Errors use `{ statusCode, message, error?, path, timestamp }` from the global exception filter.
- All routes require a valid session and an acceptable role unless declared otherwise.
- Feature modules live in `src/modules/<feature>/` and are registered in `src/app.module.ts`.
- Imports use relative paths with `.js` extensions (NodeNext ESM); path aliases are intentionally avoided.

## Environment

Validated at startup with zod — the app fails fast if a value is missing or invalid.

| Variable                    | Required  | Default                 | Notes                               |
| --------------------------- | --------- | ----------------------- | ----------------------------------- |
| `NODE_ENV`                  | no        | `development`           | `development`, `test`, `production` |
| `PORT`                      | no        | `3000`                  | positive integer                    |
| `CORS_ORIGINS`              | no        | `http://localhost:4200` | comma-separated allowlist           |
| `DATABASE_URL`              | yes       | —                       | PostgreSQL connection string        |
| `JWT_SECRET`                | yes       | —                       | at least 16 characters              |
| `JWT_EXPIRES_IN`            | no        | `15m`                   | access token lifetime               |
| `REFRESH_TOKEN_TTL_SECONDS` | no        | `604800`                | refresh token lifetime (7 days)     |
| `SEED_ADMIN_EMAIL`          | seed only | —                       | first ADMIN email                   |
| `SEED_ADMIN_PASSWORD`       | seed only | —                       | first ADMIN password                |

`Secure` is set on cookies automatically when `NODE_ENV=production`.

## Scripts

```bash
npm run build          # compile to dist/
npm run start:dev      # watch mode
npm run lint           # oxlint (type-aware)
npm run prisma:migrate # create/apply a migration
npm run prisma:seed    # create/promote the bootstrap admin
npm run prisma:studio  # inspect the database
```

Prisma 7 uses a driver adapter (`@prisma/adapter-pg`) and reads the migration URL from
`prisma.config.ts`; the schema only declares the datasource provider.
